# corev2 — backend rewrite

`corev2/` is the in-progress rewrite of the v1 backend in `core/` (Actix-web).
The package/binary is **`backend`** (Rust edition 2024): `cargo run` runs it, there
is no named bin target. The repo-root `AGENTS.md` documents v1 `core/` and the
plugin/platform behavior — most of it does **not** apply here. The `sdk/` and
`system-plugin-api/` directories are separate packages with their own builds.

Stack: axum 0.8, sqlx 0.8 (Postgres), sqlx_migrator, sea-query, utoipa (OpenAPI),
tower-http, Redis or in-memory cache, argon2 sessions.

## Commands (run from `corev2/`)

| Task     | Command                                             |
| -------- | --------------------------------------------------- |
| Run API  | `cargo run` (loads `.env` via dotenvy)              |
| Build    | `cargo build` / `cargo build --release`             |
| Tests    | `cargo test`                                        |
| Coverage | `./run_tests.sh` (`cargo llvm-cov nextest`)         |
| API spec | `GET /api/docs/openapi.json` (generated by utoipa)  |

- Tests are DB-backed: `utils/test_utils.rs::get_app_state()` builds a real pool
  from `.env` and refreshes the schema, so a reachable Postgres is required.
- `.cargo/config.toml` forces `clang` + `mold` on Linux. Without `mold` installed
  builds fail; override via `RUSTFLAGS` or remove that entry.

## Local setup gotchas

- Copy `.env.example` → `.env`; it is gitignored and `config.rs` panics when
  `DATABASE_URL` is missing.
- `docker-compose.yaml` starts **only** Postgres + pgAdmin. It creates DB
  `postgres`, but `DATABASE_URL` targets `plugin_core` — create that DB or change
  the URL. There is **no Redis** service, so the default `.env`
  (`CACHE_STRATEGY=redis`) fails; use `CACHE_STRATEGY=in_memory` locally.
- `config.rs` defaults `CORE_PORT=3000`; `.env` sets 8080. Trust `.env`.
- `Dockerfile`, `Dockerfile.k8s`, and `runDockerswarmCargoWithEnvFile.sh` are
  stale v1 copies (reference `core/`, package `bins`, binary `dockerswarm`) and do
  not build this package.
- The middleware directory is misspelled `src/middelware/` — keep using it.
- `DEV_MODE`, `PLUGINS_DIR`, `CORE_MIGRATIONS_DIR`, `FILES_DIR`, and the registry
  vars in `.env` are v1 leftovers; corev2's `config.rs` ignores them.

## Architecture

- Entrypoint `src/main.rs`: config → pool → run system + app migrations → build
  `AppState` (pool, schema cache, event bus, config, cache) → refresh schema →
  `ensure_default` version → register system hooks → trigger `core.loaded` → serve.
- Routers: `src/app.rs` (`/api/app`), `src/platform.rs` (`/api/platform`).
  - `/api/app/{items/{collection}, collections, settings}` — app-scoped.
  - `/api/platform/{auth, users, sessions, apps, versions, developer-keys, settings}`
    plus `/api/platform/me/apps`.
- **Multi-tenant schemas.** Each app×version gets its own Postgres schema named
  `{app}010{version}` (`AppContext::schema_name()` + `utils::slugify`), e.g.
  `default010v1`. Global tables live in the `alcedo` schema. The literal `010`
  separator matters: `inspector.rs` discovers schemas via
  `table_schema like '%010%' or table_schema = 'alcedo'`.
- `AppContext` selects the schema for every query. App-scoped handlers take
  `ExtractContext`, which **requires `X-App` and `X-Version` headers**; platform
  code uses `AppContext::system()`.
- Migrations are two sqlx_migrator tracks, both auto-run at startup:
  - `migrations/system_migrations/` → `alcedo` schema.
  - `migrations/app_migrations/` → per app-version schema; loops over
    `alcedo_apps_versions` and is re-run when a version is linked/cloned.
  Add one by creating `m000NN_*.rs` and registering it in that dir's `mod.rs`
  (`vec_box!`). Never edit an applied migration.
- DDL is declared in Rust via the custom `TableBuilderExt` DSL
  (`services/postgres/tables.rs`: `add_col`, `add_fk`, `TableService::create_table`),
  not raw SQL. The in-memory `DatabaseSchema` is introspected from
  `information_schema` (`inspector.rs`); call `AppState::refresh_schema()` after DDL.
- Items/collections are generic over introspected tables: `ItemsService` +
  `services/items/query.rs::Query` (sea-query). Filter/fields/sort/limit syntax is
  documented in `api-docs/query.md` and embedded in the OpenAPI docs. `item_map!`
  (`services/items/mod.rs`) is the shorthand for item payload maps.
- Events: `MultiEventBus` (`services/hooks/`), keyed by `(name, TypeId)`. System
  hooks live in `hooks/systemhooks`, event types in `hooks/types`; hooks run inside
  the caller's DB transaction (`HookContext.tx`).
- Auth (`middelware/auth.rs`): session cookie (default `alcedo_session`, resolved
  via the cache in `services/sessions.rs`) or `Authorization: Bearer <dev-key>`.
  Developer keys are **version-scoped** and also require `X-App`/`X-Version`.
  `controllers::require_admin` gates admin-only handlers.
- Errors: `services/errors.rs::AlcedoError` (variants carry a numeric code);
  Postgres errors are translated in `postgres/pool.rs::process_query_error_response`.

## Conventions

- All responses use the JSend envelope from `services/respond.rs` (`success`,
  `fail`, `error`, `JSendResponse`) — don't return bare JSON.
- New routes must be annotated with `#[utoipa::path]` **and** listed in
  `controllers/docs.rs::ApiDoc`, or they won't appear in OpenAPI.
- Non-standard test file: `services/respond.test.rs` is wired via `#[path]` in
  `respond.rs`; follow that pattern for sibling test files.
- SQL is built dynamically (sea-query / strings) and run with `sqlx::query`; the
  project does not use `#[sqlx::test]` or compile-time query macros.
